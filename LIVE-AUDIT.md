# Phase 04A audit

Reviewed the existing MainActivity, VoiceSessionManager, AssistantViewModel, AssistantRepository, Provider, SettingsRepository, Compose navigation, manifest, Gradle configuration and existing tests before adding this connection foundation. Existing implementation had foreground SpeechRecognizer/Chat/TTS, OpenAI-compatible SSE, per-provider encrypted credentials and local chat history. There was no native transport, live protocol, backend auth, SDP exchange or GPT-Live ready event. UI and voice state were controlled by both the ViewModel and fallback manager. Fallback disables recognition during TTS and cannot barge in. Existing profile capability flags are user configured, not discovery or verification.

The new isolated GPT-Live screen/controller is authoritative for its connection state. It does not overwrite text-provider profiles, settings, history or their encryption fields. Backend tokens use separate encrypted preference fields with the existing Android Keystore AES key. The existing fallback is stopped before native capture starts; leaving the live screen releases it so fallback/text speech cannot accidentally own audio simultaneously. Screen and activity lifecycle cleanup both exist, and repeated native release is idempotent. Epoch checks reject delayed transport and event callbacks after cleanup/restart. Audio focus is acquired for live communication and restored after release. Negotiation, ICE gathering, backend exchange, session-ready waiting and graceful close all have bounded timeouts.

Only GPT-Live session.started/session.closed and provider error events are handled in this connection phase. Backend uses JSON POST /v1/live/sessions with model gpt-live-1 and no legacy Realtime commands. The API session model and endpoint were checked against the user-specified official documentation, which returned HTTP 200. Android's maintained WebRTC library handles native audio media; no application fake microphone or audio chunks exist. Session and SDP contents are not logged. Backend permanent key is never delivered to Android. Custom backend hosts must be trusted because they receive the separately provisioned backend user token and SDP.

Remaining concerns requiring actual devices/account: native audio capture/playback, routes, focus interruptions, resource release, TLS deployment and account GPT-Live access; server finalization after emergency cleanup/cancelled negotiation; battery and native callback behavior. Initialization can be billable even if the client cancels before receiving the result. The single-process backend auth/rate limits require operational token provisioning, expiry/revocation and TLS reverse proxy; multi-instance deployment needs shared limits. No realtime delegation, advanced interruption, transcript display, voice memory or automation has been introduced.

# Phase 04B audit and implemented changes

Audited Phase 04A's PeerConnection, audio sender, SDP/ICE sequencing, `oai-events` channel, backend authentication, session readiness/epochs, foreground lifecycle and release paths before editing. The microphone track was already attached with `addTrack`, and remote audio was enabled through `onAddTrack`; this was real WebRTC source, not evidence that capture or delivery worked on a device. Missing pieces: record/playout callbacks and errors, sender attachment validation, native audio meters, remote track retention/disable, capture/playout controls, route management, RTP counters, captions and audio-state reporting. Graceful Stop could leave native audio active until finalization. Cleanup could stop at the first exception. Typed fallback TTS could continue after backgrounding or overlap a newly started recognition loop.

The implementation adds native JavaAudioDeviceModule capture/playout PCM and state/error callbacks, validated sender attachment, retained receiver-owned audio tracks, supported PeerConnection audio recording/playout switches, local microphone mute and safe remote disable. Remote playback is WebRTC native, never Android TTS. RTP stats are shown only when actually reported and are explicitly local evidence, not proof that the provider understood audio. Native media resources are released once with independent cleanup steps; failures are surfaced and recording is blocked until app restart. Stop silences capture/playout before the bounded session.close/session.closed wait. Existing generation checks also cover media callbacks, stats, device and audio-focus events. Microphone permission is checked before Start and periodically during the active session; capture errors also stop the session.

The live controller exclusively owns native connection and audio state. Engine running, remote track present, transport counters, measured audio energy and captions are independent facts. Audio-energy thresholds have hysteresis but do not claim to identify human speech semantically. Overlapping input/output is preserved. PROCESSING is defined but not inferred from silence or transcript gaps. Partial captions keep original fragments, event IDs and session timestamps and never invent completed turns.

Android 12+ uses available communication devices and setCommunicationDevice; older supported Android versions expose Speaker and System/headset. Supported Android routing decides actual Bluetooth behavior; no custom SCO transport or extra Bluetooth connection permission is introduced. The selected output disappearing stops the session rather than silently routing it elsewhere. Device selection and prior routes are restored on release where available. Hardware AEC/NS is requested only where the WebRTC SDK reports support; WebRTC negotiates sample rate/formats and owns the capture, playback, buffers and network audio.

JarvisFace is reused with measured levels and real activity color. Waveform samples come exclusively from PCM callbacks, at most 10 updates/second per direction. The orbit is decorative, and is entirely disabled when system animations are disabled. Capture/playout are measured before network/device output, not acoustic recordings of the speaker. No audio samples are retained or logged. Transcripts stay only in live screen/session memory (bounded to 256 fragments); existing chat history and encryption are not changed.

Protocol finding: current official GPT-Live conversation documentation describes full-duplex continuous audio and session.input_transcript.delta / session.output_transcript.delta with delta/start_ms/end_ms. It explicitly says there is no completed-turn event. It does not document legacy Realtime speech-start/end/VAD flags for this protocol. No such events or turn_detection parameters are invented. Conversation timing remains the GPT-Live model's documented internal behavior; this app reports local audio activity rather than fictional provider speech/processing events. The backend/session configuration and authentication remain unchanged from 04A.

This is code/build verification, not real audio verification. Actual native audio, permissions, Bluetooth, phone calls, routes, termination, and provider hearing/speaking require a real Android device and GPT-Live-enabled account. Phase 04C response cancellation/barge-in, delegation and tool workflows are not implemented here.
